Build and test

For contributors, and for anyone who wants to check the claims: everything on this page runs in a clone of the repository. To validate invoices with the released version, 0.1.0 on crates.io, see Use it; the commands below build the workspace and check the engine, the library and the command-line tool against Saxon-HE on the CEN and Peppol corpora.

Requirements

  • rustup, Git and Bash. The toolchain is pinned in rust-toolchain.toml (Rust 1.99.1 with rustfmt and clippy); scripts/check.sh installs it when it is missing.
  • Optional: cargo-deny, actionlint, zizmor, ShellCheck, jq, wasmtime and the wasm32-unknown-unknown target (rustup target add wasm32-unknown-unknown). Without one of them, the check that needs it prints SKIPPED; in CI they are all installed, at pinned versions, and a missing one is a failure.
  • For the reference oracle and the Peppol corpus only: Java (CI uses Temurin 21) and network access the first time, to download Saxon-HE 12.10 and the XML Resolver 5.3.3 it needs, and for Peppol the pinned release, Apache Maven and the Schematron compiler.
  • For the xmllint oracle of the schema validation only: xmllint (libxml2). The tests do not need it.

Build and install from source

The released command-line tool installs from crates.io without a clone, with Rust 1.99 or later; the library is the crate einvoice-validator, documented on docs.rs:

cargo install --locked einvoice-cli
# in Cargo.toml: einvoice-validator = "0.1"

From a clone, for the current main:

git clone https://github.com/einvoice-validator/einvoice-validator.git
cd einvoice-validator
# install the pinned toolchain if needed
scripts/check.sh toolchain
cargo build --workspace --locked
# install the command-line tool, einvoice-validate
cargo install --locked --path crates/einvoice-cli

Cargo.lock is committed; every cargo command in the checks uses --locked.

Tests

# everything
cargo test --workspace --all-features --locked
# one crate
cargo test -p einvoice-xdm --locked
# the tests of a crate whose path contains a name
cargo test -p einvoice-xdm --locked every_case
# corpus checks, no Java needed
cargo test -p xtask --locked

Besides unit tests: golden tests against results produced by the reference engines, and property-based tests with proptest. None of the CEN tests needs Java or xmllint: the expected results are committed.

# the engine on all 1179 CEN cases: its canonical SVRL must equal the Saxon-HE golden
cargo test -p einvoice-xslt-exec --release --locked --test cen_equivalence -- --nocapture
# the engine on the mutation cases (CEN; Peppol too when its corpus is built)
cargo test -p einvoice-xslt-exec --release --locked --test mutation_equivalence -- --nocapture
# the library's verdicts and findings on all 1179 CEN cases
cargo test -p einvoice-validator --release --locked --test cen_corpus -- --nocapture
# the executor on synthetic probe stylesheets, against Saxon-HE results
cargo test -p einvoice-xslt-exec --locked --test probes
# the evaluator against Saxon-HE on every distinct expression of the CEN stylesheet
cargo test -p einvoice-xpath-eval --locked --test oracle
# the atomic values against Saxon-HE results
cargo test -p einvoice-xdm --locked --test oracle
# schema validation against the xmllint results
cargo test -p einvoice-xsd --locked --test oracle

The equivalence test prints 1179 cases: 1179 equal, 0 different, 0 failed, and the mutation test CEN: 504 mutation cases: 504 equal, 0 different; any difference is shown with the first line where the two reports diverge. A mutation case on which Saxon-HE stops with a dynamic error must stop the engine with the same error code; the cases where the message differs are listed, not failed.

Test corpus and reference oracle

artefacts/ holds unmodified copies of the official validation artefacts, corpus/ the test cases derived from them and, for each case, the SVRL report Saxon-HE 12.10 produces (or the error that stops it), in the canonical form of corpus/SVRL-CANONICAL.md. Besides the official examples, test files and unit tests, the corpus has mutation cases: the edits of corpus/mutations.toml applied to official examples. The format is described in corpus/README.md.

# vendored files match artefacts/*/SHA256SUMS
cargo xtask manifest
# the corpus re-derived from artefacts/, mutation cases included, matches the committed one
cargo xtask corpus
# Saxon results vs the expectations of the official unit tests
cargo xtask crosscheck
# Saxon-HE 12.10 and the XML Resolver 5.3.3 from Maven Central,
# checksums verified, into target/oracle/saxon/
scripts/fetch-saxon.sh
# Saxon-HE on all 1179 cases and 504 mutation cases: results must equal the committed ones
cargo xtask oracle
# all of the above, then the xmllint oracle and the Saxon-HE oracles of
# einvoice-xdm, einvoice-xpath-eval and einvoice-xslt-exec
scripts/check.sh oracle

--write regenerates instead of checking (manifest, corpus, oracle). cargo xtask oracle also takes --java JAVA and --saxon JAR; scripts/check.sh oracle reads them from the JAVA and SAXON_JAR environment variables. Without Java, scripts/check.sh oracle runs the manifest, corpus and cross-check and skips the Saxon runs (in CI it fails instead). cargo test covers the manifest, extraction and cross-check without Java.

Schema validation has its own oracle, xmllint (libxml2), on 1555 cases: the corpus documents, synthetic documents and mutations of them. Every difference from xmllint is listed with its cause in crates/einvoice-xsd/tests/oracle/.

# run xmllint on every case, check the committed results, compare
cargo run --release --locked -p einvoice-xsd --example xmllint-oracle

Peppol corpus and bundle

The Peppol BIS Billing 3.0 files carry no licence, so neither they nor anything derived from them is committed: the corpus is built locally in target/peppol/. scripts/fetch-peppol.sh downloads the pinned 3.0.22 release and compiles its Peppol and CEN Schematron to XSLT with the ISO skeleton of ph-schematron, every input and output checked against a pinned checksum, and writes the bundle.toml that makes the directory a rule-set bundle. CI builds the corpus and runs these checks whenever the engine or the tooling changes.

# the release and its two compiled stylesheets, checksums verified,
# into target/peppol/peppol-bis-billing-ubl-3.0.22/, with its bundle.toml
scripts/fetch-peppol.sh
# 707 cases and 505 mutation cases, the Saxon-HE results of both
# stylesheets, and the cross-check with the official unit tests
cargo xtask peppol
# the engine on all 707 cases, with each stylesheet
cargo test -p einvoice-xslt-exec --release --locked --test peppol_equivalence -- --nocapture
# einvoice-validate with the Peppol bundle, against the same results
cargo test -p einvoice-cli --release --locked --test peppol_bundle -- --nocapture
# all of the above, and the Peppol mutation cases
scripts/check.sh peppol
# the bundle, used by the command-line tool
einvoice-validate --bundle target/peppol/peppol-bis-billing-ubl-3.0.22 invoice.xml

The equivalence test prints PEPPOL-EN16931-UBL: 707 cases: 707 equal, 0 different, 0 failed and the same for CEN-EN16931-UBL, the CEN rules the Peppol release embeds (the bundle.toml gives them the CEN version their Schematron states, 1.3.16); the cross-check reports 678 unit-test cases out of 678 in agreement with Saxon-HE.

Performance

Release builds, one machine. Reading the files is not timed by the examples; it is in the command-line runs.

# the stylesheet alone: load and prepare, then every CEN corpus document
# parsed, transformed and written as SVRL, one after the other on one thread
cargo run --release --locked -p einvoice-xslt-exec --example bench-cen -- --repeat 5
# its heap: the prepared stylesheet, the peak for one document, the whole run
cargo run --release --locked -p einvoice-xslt-exec --example heap-cen
# the whole validation (XML, schema, stylesheet) with the built-in rule set
cargo run --release --locked -p einvoice-validator --example bench
cargo run --release --locked -p einvoice-validator --example heap
# the Peppol job, both stylesheets (needs the Peppol corpus)
cargo run --release --locked -p einvoice-xslt-exec --example bench-peppol -- --repeat 5
cargo run --release --locked -p einvoice-xslt-exec --example heap-peppol
  • Stylesheet. Load about 17 ms and prepare about 5 ms, then 1179 documents (4.6 MB) in about 0.48 s: 0.4 ms per document on average, a median of 0.3 ms, about 4 ms for the slowest. The prepared stylesheet keeps about 3.7 MiB of heap. On the largest corpus document (3.3 MB), the transformation peaks at about 3.2 MiB above it when given the text as a String, which the tree keeps, and at about 6.3 MiB when the tree copies the text.
  • Whole validation. Loading the built-in rule set takes about 39 ms (the UBL 2.1 schemas 14 ms, the stylesheet 17 ms); the 1179 documents then take about 0.56 s, 0.47 ms each on average, 90 % of it in the stylesheet, 2.4 % in the schema check. The loaded rule set keeps about 5.4 MiB; the largest document peaks at about 12.3 MiB above it.
  • Peppol. Both stylesheets prepared in about 29 ms, keeping about 5.2 MiB; 707 documents (2.0 MB), each through both, in about 0.72 s, 1.0 ms per document on average.
  • Command line. einvoice-validate --format json on the 1179 CEN corpus documents, process start, rule-set load and file reading included: about 0.62 s with one thread, 0.13 s with --jobs 8; with the Peppol bundle on the 707 Peppol documents, 0.86 s and 0.16 s; on one invoice, about 50 ms.
  • Saxon-HE 12.10, for comparison. One net.sf.saxon.Transform of the CEN stylesheet alone, no schema validation, over a directory of the 1179 documents: about 1.4 s with -threads:1 and 1.0 s with -threads:8, JVM start and stylesheet compilation included.
  • WebAssembly. wasm-validate, which embeds the UBL 2.1 schemas and the CEN stylesheet, is 6.5 MB as built by the wasm job and 5.4 MB with opt-level = "z", LTO, one codegen unit and stripping (for example through the CARGO_PROFILE_RELEASE_* variables); both import nothing and return 0 under wasmtime.

Repository layout

crates/einvoice-xpath
Parser and syntax tree for the XPath 2.0 subset of the official stylesheets, XSLT match patterns, sequence types and attribute value templates.
crates/einvoice-xdm
Atomic values of the XPath 2.0 data model: exact xs:decimal, xs:integer, xs:double, dates, casts, comparisons, regular expressions, with the behaviour of Saxon-HE 12.10.
crates/einvoice-xpath-eval
Node model and evaluator of the XPath 2.0 subset, with the behaviour of Saxon-HE 12.10; unknown functions and variables are refused when an expression is compiled. The clock is an input, so it runs on wasm32-unknown-unknown.
crates/einvoice-xslt
Loader for the XSLT 2.0 subset: templates, modes, priorities, functions, variables and instructions; anything outside the subset is a load error.
crates/einvoice-xslt-exec
Executor of that subset: a stylesheet is prepared once and run on any number of documents, writing the result (SVRL for the rule sets) straight to XML. Constructs whose result would differ from Saxon's are refused when the stylesheet is prepared.
crates/einvoice-svrl
The canonical, line-oriented form of SVRL reports, shared by the oracle and the equivalence tests.
crates/einvoice-xsd
XML Schema validation of UBL 2.1 Invoice and CreditNote documents against the official OASIS schemas, which it embeds; exactly the XML Schema 1.0 constructs those schemas use, any other refused at load.
crates/einvoice-validator
The public crate: rule-set bundles (a bundle.toml manifest with the SHA-256 of each stylesheet, from memory or a directory; CEN EN 16931 UBL 1.3.17 built in, vendored in bundles/cen-ubl/), the Validator and the Report.
crates/einvoice-cli
The einvoice-validate command-line tool: files and standard input, built-in rule sets or bundle directories, several threads, text, JSON or SVRL output, documented exit codes.
xtask
Repository tooling behind cargo xtask: manifest, corpus and mutation cases, oracle, cross-check, the Peppol corpus.
artefacts
Official validation artefacts, unmodified, with their licence and SHA256SUMS.
corpus
Test cases and their Saxon-HE results, one directory per rule set, and the mutation catalogue.
scripts
check.sh, fetch-saxon.sh, fetch-peppol.sh, freshness.sh, the release scripts and the other repository scripts.
upstream.toml
Every pinned upstream version (rule sets, Saxon-HE, toolchain, CI tools) and the files that record it; a weekly workflow reports newer releases.
RELEASING.md
The release process and the versioning policy.

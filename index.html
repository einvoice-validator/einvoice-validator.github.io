einvoice-validator

Validation of European e-invoices against the official published validation artefacts, in pure Rust: no JVM, no C library, no FFI. A library and a command-line tool that run the official stylesheets unchanged, with exact decimal arithmetic, and give the same report as Saxon-HE, rule by rule.

0.2.0 released (release notes). The library einvoice-validator (API documentation) and the command-line tool einvoice-validate (crate einvoice-cli) validate UBL 2.1 invoices and credit notes (the XML, the UBL 2.1 schema, then the official stylesheets of the rule set) and, new in 0.2.0, UN/CEFACT CII D16B invoices (the XML, then the official stylesheet; no CII XML Schema validation yet, #32). The tool picks the rule set from each document's root element. Install them from crates.io (Use it). Still pre-1.0: a minor version may change the API.

Security fix in 0.2.0: a deeply nested document no longer aborts the process with a stack overflow (#29). Documents may be nested at most 256 elements deep by default (--max-depth, ValidateOptions::max_depth), and the stylesheets' recursion is bounded in nesting and in stack: beyond a limit, the document gets an error, not a crash. Upgrade from 0.1.0 if you validate documents you do not produce yourself.

Done: CEN EN 16931 UBL and CII 1.3.17 built in, Peppol BIS Billing 3.0.22 as a bundle built locally from its pinned release; on every case of the three test corpora, official and mutated, the same SVRL report as Saxon-HE 12.10 (#3, #5, #12). Still open: XML Schema validation of CII documents (#32), publishing releases from CI with crates.io trusted publishing (#17), WebAssembly bindings and an npm package (#9), other rule sets (#12). Follow the tracking issues.

What it is

The business rules of EN 16931 and of Peppol BIS Billing 3.0 are published by CEN and OpenPeppol as Schematron, which validators run compiled to XSLT 2.0 stylesheets. einvoice-validator is an XSLT 2.0 and XPath 2.0 engine, written in Rust, that runs those stylesheets as they are published, with UBL 2.1 schema validation in front of them for UBL documents, behind a library and a command-line tool. It reads both syntaxes of EN 16931: UBL 2.1 and UN/CEFACT CII D16B.

  • The official artefacts are the rules. No rule is translated into Rust by hand. The CEN artefacts are vendored byte for byte, with their checksums; the Peppol files are fetched from their pinned release and compiled, every input and output checked against a pinned checksum.
  • A closed subset. The engine implements the XSLT and XPath the official stylesheets use, nothing more. Anything else is refused when the stylesheet is loaded, never skipped.
  • Exact numbers. xs:decimal and xs:integer are arbitrary precision, as the amount and total rules require; no floating-point stand-in.
  • The reference engine decides. The expected result is the report Saxon-HE 12.10 produces for the same document: same fired rules, same failed asserts and successful reports, with the same id, flag, location and text, in the same order. On the CEN UBL 1.3.17 corpus (1179 cases and 504 mutation cases), the CEN CII 1.3.17 corpus (24 cases and 808 mutation cases) and the Peppol BIS Billing 3.0.22 corpus (707 cases and 505 mutation cases, with each of its two stylesheets), every report is identical.
  • Bounded recursion. Every parsed document may be nested at most 256 elements deep by default (libxml2's default limit), and the stylesheets' template and function invocations are bounded in nesting and in the stack they use: a deeply nested document or a stylesheet that recurses without end ends with an error, not a stack overflow. At the default maximum depth, a validation runs on a thread with the default 2 MiB stack.
  • Pure Rust. No Java runtime, no C library, no FFI, no unsafe code. The library also runs on wasm32-unknown-unknown: CI validates documents with it under wasmtime; bindings and an npm package are pending (#9).

Use it

Install the command-line tool from crates.io, with Rust 1.99 or later (rustup):

cargo install --locked einvoice-cli                  # installs einvoice-validate

or from a clone of the repository, where the toolchain (Rust 1.99.1) is pinned in rust-toolchain.toml and installed by rustup on first use (Build and install from source):

git clone https://github.com/einvoice-validator/einvoice-validator.git
cd einvoice-validator
cargo install --locked --path crates/einvoice-cli    # installs einvoice-validate

Two rule sets are built in: cen-ubl, CEN EN 16931 UBL 1.3.17 with the UBL 2.1 schemas, and cen-cii, CEN EN 16931 CII 1.3.17 (UN/CEFACT CII D16B), without an XML schema for now (#32). Without --rules or --bundle, einvoice-validate picks the rule set of each document from its root element: cen-ubl for a UBL Invoice or CreditNote, cen-cii for a CII CrossIndustryInvoice, cen-ubl for anything else.

einvoice-validate invoice.xml                        # cen-ubl or cen-cii, from the root element of the document
einvoice-validate --rules cen-cii invoice.xml        # a built-in rule set by name: cen-ubl or cen-cii
einvoice-validate --format json --jobs 4 invoices/*.xml > report.json
einvoice-validate --format svrl - < invoice.xml      # the SVRL report, as the stylesheet wrote it
einvoice-validate --bundle DIR invoice.xml           # a rule-set bundle: DIR/bundle.toml and its stylesheets
einvoice-validate --max-depth 1000 deep.xml          # accept elements nested up to 1000 deep (default 256)

Exit status, the highest that applies: 0 every document is valid (no schema error, no finding with flag fatal); 1 a document is invalid (schema errors, fatal findings, or not well-formed XML); 2 usage error, or a file or bundle that cannot be read or is not valid; 3 a construct the engine does not support, a document beyond a limit, a stylesheet error on a document, or an internal error. Output as text (for people), json (a versioned format, for scripts) or svrl; with --jobs N, N threads share one loaded rule set and the output keeps the order of the command line. Options and the JSON format: crates/einvoice-cli/README.md.

Deeply nested documents

A document with an element nested deeper than 256 levels (the document element is at depth 1; libxml2's default limit) is refused before it is validated, with the line and column of that element: an error of kind unsupported and exit status 3 in einvoice-validate, Error::Limit in the library. --max-depth N (at most 100000) and ValidateOptions::max_depth set another maximum. The stylesheets recurse once or twice per element level, so the limit keeps a validation within a bounded call stack; their template and function invocations are bounded too, in nesting and in the stack they use (ValidateOptions::max_stack, 1.5 MiB by default), so a rule set that recurses without end fails with Error::Limit instead of overflowing the stack.

$ einvoice-validate deep.xml
deep.xml: error (unsupported): limit exceeded: document, 2:838: element nested deeper than the maximum depth of 256

Peppol BIS Billing 3.0

Its files carry no licence, so they are not part of the repository or of the crates. scripts/fetch-peppol.sh, in a clone of the repository (Java and network access the first time), downloads the pinned 3.0.22 release, compiles its two stylesheets, the Peppol rules and the CEN rules the release embeds, and writes next to them the bundle.toml that names them with their checksums. The directory is then a bundle:

scripts/fetch-peppol.sh                     # into target/peppol/
einvoice-validate --bundle target/peppol/peppol-bis-billing-ubl-3.0.22 invoice.xml

Library

A Validator is built once from a rule set (schemas loaded, stylesheets prepared), is Send + Sync, and validates any number of documents. Add it from crates.io (API documentation on docs.rs):

[dependencies]
einvoice-validator = "0.2"
use einvoice_validator::{Validator, Verdict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Built once: the UBL 2.1 schemas loaded, the CEN stylesheet prepared.
    // A Validator is Send + Sync: share it between threads.
    let validator = Validator::cen_ubl()?;
    let report = validator.validate(&std::fs::read("invoice.xml")?)?;
    for error in &report.schema_errors {
        println!("schema {}:{}: {}", error.line, error.column, error.message);
    }
    for finding in report.findings() {
        let id = finding.id.as_deref().unwrap_or("-");
        println!("{:?} {id}: {} (at {})", finding.severity, finding.text, finding.location);
    }
    println!("{}", if report.verdict() == Verdict::Valid { "valid" } else { "invalid" });
    Ok(())
}

Validator::cen_cii() is the CII rule set, and Syntax::detect tells from a document's root element which of the two built-in rule sets is its own:

use einvoice_validator::{Syntax, Validator, Verdict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let document = std::fs::read("invoice.xml")?;
    // From the root element: cen-ubl for a UBL Invoice or CreditNote,
    // cen-cii for a CII CrossIndustryInvoice.
    let rule_set = Syntax::detect(&document).map_or("cen-ubl", Syntax::builtin_rule_set);
    let validator = Validator::builtin(rule_set)?;
    let report = validator.validate(&document)?;
    let verdict = if report.verdict() == Verdict::Valid { "valid" } else { "invalid" };
    println!("{rule_set}: {verdict}");
    Ok(())
}

Validator::from_bundle_dir loads a bundle directory such as the Peppol one. The Report also gives the raw and canonical SVRL and the rule-set version; validate_owned takes the document as an owned buffer and avoids a copy of its text.

Why run the official stylesheets

The validation artefacts are the reference definition of the rules. Running them unchanged means a new release of the rules is new data to vendor and test, not code to rewrite, and a result can always be traced back to the published rule that produced it.

Quality

  • Reference results. For each rule set, the official examples, test files and unit tests, each with the SVRL report Saxon-HE 12.10 produces, in a canonical text form: 1179 CEN UBL cases, 24 CEN CII cases, 707 Peppol cases. They are cross-checked against the expectations written in the official unit tests, with no disagreement (1131 CEN UBL, 9 CEN CII and 678 Peppol unit-test cases). CI runs Saxon again and the CEN UBL and CII results must not change; the Peppol corpus is rebuilt whenever the engine changes.
  • Mutation cases. A catalogue of edits of the official examples, aimed at what the rules check and where engines can diverge: totals and rounding, decimal precision, number and date forms, VAT categories, code lists, check digits, namespaces, repeated elements. 504 CEN UBL and 505 Peppol cases; they raise the number of distinct CEN UBL asserts that fire in the corpus from 235 to 973 of 982. A second catalogue does the same for CII, with the charge indicator in every lexical form and the element or attribute each not(X) rule of CII-SR and CII-DT looks for: 808 cases, in which 785 of the 810 assert ids of the CII stylesheet fail at least once (21 in the official cases alone); the corpus README says why the 25 others cannot. Where Saxon-HE stops with a dynamic error, the engine stops with the same error code.
  • Same reports as Saxon-HE. On every case of the three corpora, the canonical report of the engine is identical to Saxon's, line for line, and the verdicts and findings of the library and of einvoice-validate agree with them. Each crate is also checked on its own: the atomic values against Saxon-HE on over 5000 operations, the evaluator on every distinct expression of the CEN stylesheet (956) at nodes of corpus documents, the executor on synthetic probe stylesheets. Decimal casts and division follow the static types Saxon-HE infers for variables, parameters and function results, as in a stylesheet (#21).
  • Schema validation compared with xmllint. 1555 cases: the 1179 corpus documents, synthetic documents and mutations of them. Every corpus document gets the same result. Every other difference is listed with its cause: cases where libxml2 departs from XML Schema 1.0, and signature content checked loosely because the two ETSI XAdES schemas are not shipped. The constructs the CII-family schemas add (fixed and default values, anonymous complex types in local elements, length facets on strings) are compared with xmllint on a synthetic suite of 180 document cases and 69 schema mutations.
  • Speed (measured with 0.1.0). einvoice-validate --format json on the whole CEN UBL corpus (1179 documents, 4.6 MB), XML, schema and stylesheet checks, process start and rule-set load included, takes about 0.6 s with one thread and 0.13 s with --jobs 8; a single invoice about 50 ms. Saxon-HE 12.10, running the stylesheet alone (no schema validation) over the same documents, takes about 1.4 s with one thread and 1.0 s with eight, JVM start and stylesheet compilation included. With the Peppol bundle, the 707 Peppol documents (both stylesheets) take about 0.86 s, or 0.16 s with eight threads. In 0.2.0, the schema stage takes 23 % less time on the corpus. Commands and details: Build and test.
  • Memory. In 0.2.0 the schema validation copies no values out of the document: on the largest CEN corpus document (3.3 MB), given as a buffer, its peak above the input drops from 9.4 MiB to 53 KiB and the peak of the whole validation from 12.6 MiB to 3.3 MiB; the compiled UBL 2.1 schema keeps 0.9 MiB instead of 1.7 MiB.
  • WebAssembly size (measured with 0.1.0). The wasm-validate example, which embeds the UBL 2.1 schemas (2.9 MB) and the CEN stylesheet (0.9 MB), is 6.5 MB in a release build and 5.4 MB with opt-level = "z", LTO, one codegen unit and stripping; it imports nothing.
  • Integrity. Vendored artefacts are checked against their SHA-256 sums, and so are the Peppol release, the compiled Peppol stylesheets and the stylesheets of every bundle; Saxon-HE and the XML Resolver it needs, used only in tests, are downloaded from Maven Central and their checksums verified. CI and the fetch scripts retry failed downloads and cache the tool archives and Saxon-HE jars, checked against their pinned checksums.
  • Lints. Every warning is an error; clippy all and pedantic are denied; unwrap, expect and panic are denied outside tests; unsafe code is forbidden.
  • Tests. Unit, golden and property-based tests (proptest); on Linux for every push to main, also on macOS and Windows for pull requests; the library without its built-in rule set, and on wasm32-unknown-unknown under wasmtime.
  • Supply chain. Toolchain pinned (Rust 1.99.1), Cargo.lock committed and every cargo command --locked; licences, advisories and sources checked by cargo-deny; GitHub Actions pinned by commit SHA, linted by actionlint and audited by zizmor; signed commits. Dependabot and a weekly check report newer versions of the pinned upstreams: rule sets, Saxon-HE, toolchain, CI tools.
  • Releases. A changelog checked on every pull request, and a release script and workflow that check the tag, the workspace version and the changelog agree. Each release states the rule-set versions it was tested against; the latest, 0.2.0, was tested against the CEN EN 16931 validation artefacts 1.3.17 (UBL and CII) and Peppol BIS Billing 3.0.22.
  • Same checks everywhere. CI and a local run use the same script: see Build and test.

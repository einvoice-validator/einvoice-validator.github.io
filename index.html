einvoice-validator

Validation of European e-invoices against the official published validation artefacts, in pure Rust: no JVM, no C library, no FFI. A library and a command-line tool that run the official stylesheets unchanged, with exact decimal arithmetic, and give the same report as Saxon-HE, rule by rule.

Pre-alpha, no release yet: usable from source. The library einvoice-validator and the command-line tool einvoice-validate validate UBL 2.1 invoices and credit notes: the XML, the UBL 2.1 schema, then the official stylesheets of the rule set. Install them from a clone of the repository (Use it); nothing is published on crates.io, and before 1.0 the API may change.

Done: CEN EN 16931 UBL 1.3.17 built in, Peppol BIS Billing 3.0.22 as a bundle built locally from its pinned release; on every case of both test corpora, official and mutated, the same SVRL report as Saxon-HE 12.10 (#3, #5). Still open: the first release (#17), WebAssembly bindings and an npm package (#9), other rule sets (#12). Follow the tracking issues.

What it is

The business rules of EN 16931 and of Peppol BIS Billing 3.0 are published by CEN and OpenPeppol as Schematron, which validators run compiled to XSLT 2.0 stylesheets. einvoice-validator is an XSLT 2.0 and XPath 2.0 engine, written in Rust, that runs those stylesheets as they are published, with UBL 2.1 schema validation in front of them, behind a library and a command-line tool.

  • The official artefacts are the rules. No rule is translated into Rust by hand. The CEN artefacts are vendored byte for byte, with their checksums; the Peppol files are fetched from their pinned release and compiled, every input and output checked against a pinned checksum.
  • A closed subset. The engine implements the XSLT and XPath the official stylesheets use, nothing more. Anything else is refused when the stylesheet is loaded, never skipped.
  • Exact numbers. xs:decimal and xs:integer are arbitrary precision, as the amount and total rules require; no floating-point stand-in.
  • The reference engine decides. The expected result is the report Saxon-HE 12.10 produces for the same document: same fired rules, same failed asserts and successful reports, with the same id, flag, location and text, in the same order. On the CEN UBL 1.3.17 corpus (1179 cases and 504 mutation cases) and on the Peppol BIS Billing 3.0.22 corpus (707 cases and 505 mutation cases, with each of its two stylesheets), every report is identical.
  • Pure Rust. No Java runtime, no C library, no FFI, no unsafe code. The library also runs on wasm32-unknown-unknown: CI validates documents with it under wasmtime; bindings and an npm package are pending (#9).

Use it

There is no release yet: install the command-line tool from a clone of the repository. The toolchain (Rust 1.99.1) is pinned in rust-toolchain.toml and installed by rustup on first use.

git clone https://github.com/einvoice-validator/einvoice-validator.git
cd einvoice-validator
cargo install --locked --path crates/einvoice-cli    # installs einvoice-validate

The built-in rule set is CEN EN 16931 UBL 1.3.17, with the UBL 2.1 schemas:

einvoice-validate invoice.xml
einvoice-validate --format json --jobs 4 invoices/*.xml > report.json
einvoice-validate --format svrl - < invoice.xml      # the SVRL report, as the stylesheet wrote it
einvoice-validate --bundle DIR invoice.xml           # a rule-set bundle: DIR/bundle.toml and its stylesheets
$ einvoice-validate invoice.xml broken.xml
invoice.xml: valid
broken.xml: invalid: 1 schema error, 11 fatal
  schema   2:1: missing-element: element ubl:Invoice: content incomplete; expected: ext:UBLExtensions, cbc:UBLVersionID, cbc:CustomizationID, cbc:ProfileID, cbc:ProfileExecutionID, cbc:ID
  ...
  fatal    BR-02: [BR-02]-An Invoice shall have an Invoice number (BT-1).
           at /*:Invoice[namespace-uri()='urn:oasis:names:specification:ubl:schema:xsd:Invoice-2'][1]
  ...
2 documents: 1 valid, 1 invalid, 0 not validated

Exit status, the highest that applies: 0 every document is valid (no schema error, no finding with flag fatal); 1 a document is invalid (schema errors, fatal findings, or not well-formed XML); 2 usage error, or a file or bundle that cannot be read or is not valid; 3 a construct the engine does not support, a stylesheet error on a document, or an internal error. Output as text (for people), json (a versioned format, for scripts) or svrl; with --jobs N, N threads share one loaded rule set and the output keeps the order of the command line. Options and the JSON format: crates/einvoice-cli/README.md.

Peppol BIS Billing 3.0

Its files carry no licence, so they are not part of the repository. scripts/fetch-peppol.sh (Java and network access the first time) downloads the pinned 3.0.22 release, compiles its two stylesheets, the Peppol rules and the CEN rules the release embeds, and writes next to them the bundle.toml that names them with their checksums. The directory is then a bundle:

scripts/fetch-peppol.sh                     # into target/peppol/
einvoice-validate --bundle target/peppol/peppol-bis-billing-ubl-3.0.22 invoice.xml

Library

A Validator is built once from a rule set (schemas loaded, stylesheets prepared), is Send + Sync, and validates any number of documents. With no release yet, depend on the repository:

[dependencies]
einvoice-validator = { git = "https://github.com/einvoice-validator/einvoice-validator" }
use einvoice_validator::{Validator, Verdict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Built once: the UBL 2.1 schemas loaded, the CEN stylesheet prepared.
    // A Validator is Send + Sync: share it between threads.
    let validator = Validator::cen_ubl()?;
    let report = validator.validate(&std::fs::read("invoice.xml")?)?;
    for error in &report.schema_errors {
        println!("schema {}:{}: {}", error.line, error.column, error.message);
    }
    for finding in report.findings() {
        let id = finding.id.as_deref().unwrap_or("-");
        println!("{:?} {id}: {} (at {})", finding.severity, finding.text, finding.location);
    }
    println!("{}", if report.verdict() == Verdict::Valid { "valid" } else { "invalid" });
    Ok(())
}

Validator::from_bundle_dir loads a bundle directory such as the Peppol one. The Report also gives the raw and canonical SVRL and the rule-set version; validate_owned takes the document as an owned buffer and avoids a copy of its text.

Why run the official stylesheets

The validation artefacts are the reference definition of the rules. Running them unchanged means a new release of the rules is new data to vendor and test, not code to rewrite, and a result can always be traced back to the published rule that produced it.

Quality

  • Reference results. For each rule set, the official examples, test files and unit tests, each with the SVRL report Saxon-HE 12.10 produces, in a canonical text form: 1179 CEN cases, 707 Peppol cases. They are cross-checked against the expectations written in the official unit tests, with no disagreement (1131 CEN and 678 Peppol unit-test cases). CI runs Saxon again and the CEN results must not change; the Peppol corpus is rebuilt whenever the engine changes.
  • Mutation cases. A catalogue of edits of the official examples, aimed at what the rules check and where engines can diverge: totals and rounding, decimal precision, number and date forms, VAT categories, code lists, check digits, namespaces, repeated elements. 504 CEN and 505 Peppol cases; they raise the number of distinct CEN asserts that fire in the corpus from 235 to 973 of 982. Where Saxon-HE stops with a dynamic error, the engine stops with the same error code.
  • Same reports as Saxon-HE. On every case of both corpora, the canonical report of the engine is identical to Saxon's, line for line, and the verdicts and findings of the library and of einvoice-validate agree with them. Each crate is also checked on its own: the atomic values against Saxon-HE on over 5000 operations, the evaluator on every distinct expression of the CEN stylesheet (956) at nodes of corpus documents, the executor on synthetic probe stylesheets.
  • Schema validation compared with xmllint. 1546 cases: the 1179 corpus documents, synthetic documents and mutations of them. Every corpus document gets the same result; the 25 verdicts that differ are cases where libxml2 departs from XML Schema 1.0, each listed with its cause.
  • Speed. einvoice-validate --format json on the whole CEN corpus (1179 documents, 4.6 MB), XML, schema and stylesheet checks, process start and rule-set load included, takes about 0.6 s with one thread and 0.13 s with --jobs 8; a single invoice about 50 ms. Saxon-HE 12.10, running the stylesheet alone (no schema validation) over the same documents, takes about 1.4 s with one thread and 1.0 s with eight, JVM start and stylesheet compilation included. With the Peppol bundle, the 707 Peppol documents (both stylesheets) take about 0.86 s, or 0.16 s with eight threads. Commands and details: Build and test.
  • Memory. Loaded, the built-in rule set (schemas and prepared stylesheet) keeps about 5.4 MiB of heap; validating the largest corpus document (3.3 MB) peaks at about 12.3 MiB above it, in the schema stage. The stylesheet stage alone peaks at about 3.2 MiB above the prepared stylesheet on that document when it is given the text, which its tree then keeps instead of copying (6.3 MiB when it copies it).
  • WebAssembly size. The wasm-validate example, which embeds the UBL 2.1 schemas (2.9 MB) and the CEN stylesheet (0.9 MB), is 6.5 MB in a release build and 5.4 MB with opt-level = "z", LTO, one codegen unit and stripping; it imports nothing.
  • Integrity. Vendored artefacts are checked against their SHA-256 sums, and so are the Peppol release, the compiled Peppol stylesheets and the stylesheets of every bundle; Saxon-HE and the XML Resolver it needs, used only in tests, are downloaded from Maven Central and their checksums verified.
  • Lints. Every warning is an error; clippy all and pedantic are denied; unwrap, expect and panic are denied outside tests; unsafe code is forbidden.
  • Tests. Unit, golden and property-based tests (proptest); on Linux for every push to main, also on macOS and Windows for pull requests; the library without its built-in rule set, and on wasm32-unknown-unknown under wasmtime.
  • Supply chain. Toolchain pinned (Rust 1.99.1), Cargo.lock committed and every cargo command --locked; licences, advisories and sources checked by cargo-deny; GitHub Actions pinned by commit SHA, linted by actionlint and audited by zizmor; signed commits. Dependabot and a weekly check report newer versions of the pinned upstreams: rule sets, Saxon-HE, toolchain, CI tools.
  • Releases. A changelog checked on every pull request, and a release script and workflow that check the tag, the workspace version and the changelog agree. No release yet.
  • Same checks everywhere. CI and a local run use the same script: see Build and test.

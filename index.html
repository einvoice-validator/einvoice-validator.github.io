einvoice-validator

Validation of European e-invoices against the official published validation artefacts, in pure Rust: no JVM, no C library, no FFI. A library and a command-line tool that run the official stylesheets unchanged, with exact decimal arithmetic, and give the same report as Saxon-HE, rule by rule.

0.4.0 released (release notes). The library einvoice-validator (API documentation on docs.rs) and the command-line tool einvoice-validate (crate einvoice-cli) are on crates.io, with the eleven other crates of the workspace, all at 0.4.0. They validate UBL 2.1 invoices and credit notes and UN/CEFACT CII D16B invoices: the XML, the XML schema of the syntax, then the official stylesheets of the rule set. Install them from crates.io (Use it). Still pre-1.0: a minor version may change the API.

New in 0.4.0: the Factur-X bundles and those of the French package also validate the XML schema their reference validator runs before the stylesheets (the Factur-X schema of the profile; UN/CEFACT CII D22B, CDAR D22B), as the UBL and XRechnung bundles already did; this is a breaking change: documents that were valid only because that step was missing are now invalid, as the reference validators find them, and these rule sets must be fetched again (einvoice-validate rules fetch factur-x fr-ctc, #37). Documents in UTF-16, US-ASCII, ISO-8859-1, ISO-8859-15 and windows-1252, read as xmllint and Saxon-HE read them (0.3.0 read UTF-8 only); xsi:type naming any built-in simple type of XML Schema 1.0, unresolved IDREF values reported (#6); on WebAssembly, the maximum depth and stack capped at 400 levels and 256 KiB, within the native stacks of Chrome, Firefox and Node.js (#34); XRechnung validated faster than Saxon-HE on one thread, 2.1 times (#40, Performance). The API changes too: SchemaId is no longer Copy (release notes). Follow the tracking issues.

What it is

The business rules of EN 16931 and of the specifications built on it (Peppol BIS Billing 3.0, XRechnung, Factur-X, the French e-invoicing rules) are published as Schematron, which validators run compiled to XSLT 2.0 stylesheets. einvoice-validator is an XSLT 2.0 and XPath 2.0 engine, written in Rust, that runs those stylesheets as they are published, with XML Schema validation in front of them, behind a library and a command-line tool. It reads both syntaxes of EN 16931: UBL 2.1 and UN/CEFACT CII D16B, as XML files or embedded in a Factur-X, ZUGFeRD or Order-X PDF file.

  • The official artefacts are the rules. No rule is translated into Rust by hand. The CEN artefacts are vendored byte for byte, with their checksums; the other rule sets are downloaded from their publishers at pinned URLs, every file checked against a pinned digest.
  • A closed subset. The engine implements the XSLT and XPath the official stylesheets use, nothing more. Anything else is refused when the stylesheet is loaded, never skipped.
  • Exact numbers. xs:decimal and xs:integer are arbitrary precision, as the amount and total rules require; no floating-point stand-in.
  • The reference engine decides. The expected result is the report Saxon-HE 12.10 produces for the same document: same fired rules, same failed asserts and successful reports, with the same id, flag, location and text, in the same order. On every case and mutation case of the test corpus of every rule set below, with each of its stylesheets, the report is identical (Rule sets).
  • Verdicts as the reference validators give them. A Factur-X failed assert without a flag is fatal, as the Mustang validator reads it; XRechnung documents are validated by the scenarios of the KoSIT validator configuration, as the KoSIT validator runs them. On every corpus document, each rule set reads the reports as its reference validator does (the XML schema step of Factur-X and the French rules included, since 0.4.0, #37).
  • Bounded. Depth and nesting limits on documents and stylesheets: a hostile input ends with an error, not a crash (Security).
  • Pure Rust. No Java runtime, no C library, no FFI, no unsafe code, no C or assembly file built (Pure Rust). The library also runs on wasm32-unknown-unknown.

Use it

Install the command-line tool from crates.io, with Rust 1.99 or later (rustup):

cargo install --locked einvoice-cli                  # installs einvoice-validate

or from a clone of the repository, where the toolchain (Rust 1.99.1) is pinned in rust-toolchain.toml and installed by rustup on first use (Build and install from source):

git clone https://github.com/einvoice-validator/einvoice-validator.git
cd einvoice-validator
cargo install --locked --path crates/einvoice-cli    # installs einvoice-validate

Two rule sets are built in: cen-ubl, CEN EN 16931 UBL 1.3.17 with the UBL 2.1 schemas, and cen-cii, CEN EN 16931 CII 1.3.17 with the UN/CEFACT CII D16B schemas. Without --rules or --bundle, einvoice-validate picks the rule set of each document from its root element: cen-ubl for a UBL Invoice or CreditNote, cen-cii for a CII CrossIndustryInvoice, cen-ubl for anything else. The other rule sets are fetched on demand (below).

einvoice-validate invoice.xml                        # cen-ubl or cen-cii, from the root element of the document
einvoice-validate factur-x.pdf                       # a Factur-X / ZUGFeRD / Order-X PDF: the invoice XML it embeds
einvoice-validate --rules cen-cii invoice.xml        # a built-in rule set by name: cen-ubl or cen-cii
einvoice-validate --rules xrechnung invoice.xml      # a rule set fetched on demand (rules fetch xrechnung first)
einvoice-validate --format json --jobs 4 invoices/*.xml > report.json
einvoice-validate --format svrl - < invoice.xml      # the SVRL report, as the stylesheet wrote it
einvoice-validate --bundle DIR invoice.xml           # a rule-set bundle: DIR/bundle.toml and its stylesheets
einvoice-validate --fail-closed invoice.xml          # a finding of no known severity is fatal
einvoice-validate --max-depth 1000 deep.xml          # accept elements nested up to 1000 deep (default 256)
einvoice-validate --licences                         # the licences of everything the binary embeds, in full

Exit status, the highest that applies: 0 every document is valid (no schema error, no fatal finding); 1 a document is invalid (schema errors, fatal findings, not well-formed XML, or, for XRechnung, no matching scenario); 2 usage error, or a file or bundle that cannot be read or is not valid (a PDF file without one embedded invoice included); 3 a construct the engine does not support (an encrypted PDF file included), a document beyond a limit, a stylesheet error on a document, or an internal error. Output as text (for people), json (a versioned format, for scripts) or svrl; with --jobs N, N threads share one loaded rule set and the output keeps the order of the command line. Options and the JSON format: crates/einvoice-cli/README.md.

PDF files

A file or standard input that starts with %PDF- is read as a Factur-X, ZUGFeRD or Order-X PDF/A-3 file, by the crate einvoice-pdf, in pure Rust: the embedded invoice XML is extracted byte for byte and validated with the rule set of its root element (or the one named), and the output adds what the PDF states about it: the embedded file, its /AFRelationship, the PDF/A identification and the Factur-X / ZUGFeRD properties of its XMP metadata. The reader takes only the part of PDF on the path to embedded files and bounds every resource against hostile input; an encrypted file or a PDF feature outside that part is refused (exit status 3). In the library: the feature pdf, on by default, and pdf::extract.

Deeply nested documents

A document with an element nested deeper than 256 levels (the document element is at depth 1; libxml2's default limit) is refused before it is validated, with the line and column of that element: an error of kind unsupported and exit status 3 in einvoice-validate, Error::Limit in the library. --max-depth N (at most 100000) and ValidateOptions::max_depth set another maximum. The other limits are listed under Security.

$ einvoice-validate deep.xml
deep.xml: error (unsupported): limit exceeded: document, 2:838: element nested deeper than the maximum depth of 256

Rule sets fetched on demand

Peppol BIS Billing 3.0, XRechnung, Factur-X and the French e-invoicing rules may not be redistributed, so they are not part of the crates. einvoice-validate downloads them from their publishers only when asked (rules fetch NAME, a family, an alias or --all; or --fetch in a validation run), at pinned URLs, checks every file against its pinned digest, assembles their bundles in a local cache (EINVOICE_VALIDATOR_CACHE, by default the platform cache directory) and then works offline. rules list shows the rule sets, their sources and what is cached.

einvoice-validate rules fetch xrechnung              # once, from KoSIT's package registry
einvoice-validate --rules xrechnung invoice.xml      # xrechnung-ubl or xrechnung-cii, from the document's syntax
einvoice-validate rules fetch peppol                 # the Peppol Schematron, compiled here, in Rust
einvoice-validate --rules peppol invoice.xml
einvoice-validate --rules factur-x-en16931 --fetch invoice.pdf   # fetch in this run if missing
einvoice-validate rules list                         # every rule set, its source, cached or not
einvoice-validate rules path factur-x-en16931        # the bundle directory, for --bundle
  • Peppol, without Java. OpenPeppol publishes the rules as Schematron only. rules fetch peppol compiles them as ph-schematron 10.3.1 compiles them for the reference validators, in this program: the ISO Schematron skeleton, taken from the pinned jar of ph-schematron-isosch on Maven Central, is run by the engine (crate einvoice-schematron), and both stylesheets come out byte for byte those of ph-schematron, their SHA-256 pinned.
  • XRechnung, as the KoSIT validator runs it. The bundles hold every scenario of the KoSIT validator configuration for their syntax (7 for UBL, 4 for CII): the match expression of each scenario is evaluated on the document, the one that matches names the stylesheets that run (the CEN rules alone, or the CEN and XRechnung rules) and the levels it gives some rule ids, and a document that matches no scenario, or several, is invalid. The document is first validated against the XML schema of its scenario: UBL 2.1, or UN/CEFACT CII D16B.
  • Verdicts as the reference validators give them. A Factur-X failed assert without a flag (most have none) is fatal, as the Mustang validator reads it, and so is an XRechnung one, as the KoSIT validator reads it. On every document of the test corpora, each bundle reads the Saxon-HE reports as the reference validator does, and the XRechnung bundles validate the XML schema of the scenario first, as the KoSIT validator does. Since 0.4.0, the Factur-X and French bundles validate the XML schema their reference validator runs too (the Factur-X schema of the profile as Mustang selects it; UN/CEFACT CII D22B, CDAR D22B or the Factur-X schema, as the FNFE-MPE package documents it), fetched with the rule sets and not redistributed, so that on every corpus document their verdict is the reference validator's, schema step included (#37). --fail-closed (ValidateOptions::fail_closed) makes every other finding of no known severity fatal.
  • Downloads in pure Rust. HTTPS through rustls, on a cryptography provider built on the RustCrypto crates: no C, no assembly file. It is the feature fetch of einvoice-cli, on by default; cargo install einvoice-cli --no-default-features builds a tool without network code.

Library

A Validator is built once from a rule set (schemas loaded, stylesheets prepared), is Send + Sync, and validates any number of documents. Add it from crates.io (API documentation on docs.rs):

[dependencies]
einvoice-validator = "0.4"
use einvoice_validator::{Validator, Verdict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Built once: the UBL 2.1 schemas loaded, the CEN stylesheet prepared.
    // A Validator is Send + Sync: share it between threads.
    let validator = Validator::cen_ubl()?;
    let report = validator.validate(&std::fs::read("invoice.xml")?)?;
    for error in &report.schema_errors {
        println!("schema {}:{}: {}", error.line, error.column, error.message);
    }
    for finding in report.findings() {
        let id = finding.id.as_deref().unwrap_or("-");
        println!("{:?} {id}: {} (at {})", finding.severity, finding.text, finding.location);
    }
    println!("{}", if report.verdict() == Verdict::Valid { "valid" } else { "invalid" });
    Ok(())
}

Validator::cen_cii() is the CII rule set, and Syntax::detect tells from a document's root element which of the two built-in rule sets is its own:

use einvoice_validator::{Syntax, Validator, Verdict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let document = std::fs::read("invoice.xml")?;
    // From the root element: cen-ubl for a UBL Invoice or CreditNote,
    // cen-cii for a CII CrossIndustryInvoice.
    let rule_set = Syntax::detect(&document).map_or("cen-ubl", Syntax::builtin_rule_set);
    let validator = Validator::builtin(rule_set)?;
    let report = validator.validate(&document)?;
    let verdict = if report.verdict() == Verdict::Valid { "valid" } else { "invalid" };
    println!("{rule_set}: {verdict}");
    Ok(())
}

Validator::from_bundle_dir loads a bundle directory, and with the feature fetch, Validator::from_cache a rule set fetched on demand (RuleSetCache, fetched_rule_sets). A Validator is Clone, sharing the loaded rule set. The Report also gives the raw and canonical SVRL, the number of fired rules of each stylesheet, the scenario a document matched and the rule-set version; validate_owned takes the document as an owned buffer and avoids a copy of its text.

Why run the official stylesheets

The validation artefacts are the reference definition of the rules. Running them unchanged means a new release of the rules is new data to vendor and test, not code to rewrite, and a result can always be traced back to the published rule that produced it.

Performance

einvoice-validate against Saxon-HE 12.10 running the same official stylesheets on the same documents: the whole corpus of each rule set (every document, mutation cases included), one process per job, process start and rule-set load included. There are 23 jobs, one per rule set exactly as einvoice-validate --rules NAME runs it (#41): the rule set read from the cache rules fetch fills, the XML schema step, the XRechnung scenarios, the stylesheets and the verdicts, which must be the reference verdicts on every document and every run. Median of 5 runs, measured with cargo xtask bench at commit f07b7a8 (in 0.4.0), on a 20-core desktop machine (load average 1.3 before the run, 6.5 after, the run's own processes included); the full tables, the method and every run are in docs/benchmarks.md.

Security

Documents, PDF files and rule-set bundles may come from anyone; each is bounded so that a hostile one ends with an error, not a crash or an unbounded allocation.

  • Document depth. An element nested deeper than 256 levels (libxml2's default limit; --max-depth, ValidateOptions::max_depth, at most 100000) is refused before the document is validated (#29). At the default maximum, a validation runs on a thread with the default 2 MiB stack, in a debug build too.
  • Stylesheet recursion. Template and function invocations are bounded in nesting and in the stack they use (ValidateOptions::max_stack, 1.5 MiB by default; 256 KiB on WebAssembly), and tail calls of named templates to 65536 in a row: a rule set that recurses without end fails with Error::Limit instead of overflowing the stack.
  • Stylesheet nesting (new in 0.3.0, #33). A bundle whose XPath expressions or patterns nest deeper than 128 levels, or whose instructions nest deeper than 64, is refused when it is loaded, rather than overflowing the stack; the official stylesheets need 32 and 9.
  • WebAssembly (new in 0.4.0, #34). max_depth is capped at 400 and max_stack at 256 KiB (WASM_MAX_DEPTH, WASM_MAX_STACK; more is Error::OptionOutOfRange): measured in Chrome, Firefox and Node.js, on the main thread and in a Web Worker, a recursion then ends with the library's stack limit, never with an overflow of the engine's stack.
  • PDF files. Only the part of PDF on the path to embedded files is read, with every resource bounded; encrypted files and anything else are refused.
  • Bundles and downloads. Every stylesheet and every file a stylesheet reads is named in the bundle's manifest with its SHA-256, checked when the bundle is loaded, and document() reads nothing else. Downloaded rule sets are checked against pinned digests, with size limits, and their archives are read with path checks.

Report a vulnerability through the repository's security policy.

Pure Rust

  • No C, no assembly in our code. No crate of the workspace contains unsafe code (unsafe_code = "forbid"), and no C or C++ file is compiled and no assembly file assembled or linked, on any target. Big integers are our own einvoice-bigint, safe Rust without assembly.
  • Downloads on a pure-Rust TLS stack. rustls with a cryptography provider of the project on the RustCrypto crates, instead of the C and assembly of ring or aws-lc-rs; the crates that build native code are banned in deny.toml. What is downloaded is checked against its pinned digest; TLS is a second line of defence.
  • Audited dependencies. docs/dependencies.md lists, crate by crate, the third-party unsafe, build scripts and inline assembly compiled into the binary, the library and the WebAssembly module (which has no inline assembly), and a test keeps it in step with the dependency graphs.

Quality

  • Reference results. For each rule set, the official examples, test files and unit tests, each with the SVRL report Saxon-HE 12.10 produces, in a canonical text form. They are cross-checked against the expectations written in the official unit tests, with no disagreement (1131 CEN UBL, 9 CEN CII and 678 Peppol unit-test cases, and the expectations of the XRechnung Schematron's unit tests). CI runs Saxon again and the committed CEN UBL and CII results must not change; the corpora of the fetched rule sets are rebuilt and checked in CI.
  • Mutation cases. A catalogue of edits of the official examples, aimed at what the rules check and where engines can diverge: totals and rounding, decimal precision, number and date forms, VAT categories, code lists, check digits, namespaces, repeated elements, element order. 508 UBL cases make 973 of the 982 distinct CEN UBL asserts fire, against 235 with the official cases alone. A second catalogue does the same for CII: 808 cases, in which 785 of the 810 assert ids of the CII stylesheet fail at least once; the corpus README says why the 25 others cannot. Where Saxon-HE stops with a dynamic error, the engine stops with the same error code.
  • Same reports as Saxon-HE. On every case of every corpus, the canonical report of the engine is identical to Saxon's, line for line, and the verdicts and findings of the library and of einvoice-validate agree with them. Each crate is also checked on its own: the atomic values against Saxon-HE on over 5000 operations, the evaluator on every distinct expression of the CEN stylesheet at nodes of corpus documents, the executor on synthetic probe stylesheets, the Schematron compiler against ph-schematron at each step.
  • Schema validation compared with xmllint on the UBL and CII corpora, synthetic documents and mutations of them; every difference is listed with its cause: cases where libxml2 departs from XML Schema 1.0 (decimals beyond its 24 digits, for instance), and signature content checked loosely because the two ETSI XAdES schemas are not shipped.
  • Memory. A test fails when the peak heap of a validation exceeds its recorded budget. On a synthetic invoice of 5000 lines (4.1 MB), a validation peaks at 2.1 times the document, the stylesheet's input tree alone being 1.9 times.
  • Integrity. Vendored artefacts are checked against their SHA-256 sums, and so are every fetched rule set, the compiled Peppol stylesheets and every file of a bundle; Saxon-HE and the XML Resolver it needs, used only in tests, are downloaded from Maven Central and their checksums verified.
  • Lints. Every warning is an error; clippy all and pedantic are denied; unwrap, expect and panic are denied outside tests; unsafe code is forbidden.
  • Tests. Unit, golden and property-based tests (proptest); on Linux for every push to main, also on macOS and Windows for pull requests; the library without its built-in rule sets, on wasm32-unknown-unknown under wasmtime, and the npm package under Node.js and in headless browsers.
  • Supply chain. Toolchain pinned (Rust 1.99.1), Cargo.lock committed and every cargo command --locked; licences, advisories, bans and sources checked by cargo-deny; GitHub Actions pinned by commit SHA, linted by actionlint and audited by zizmor; signed commits. Dependabot and a weekly check report newer versions of the pinned upstreams: rule sets, Saxon-HE, toolchain, CI tools.
  • Releases. A changelog checked on every pull request, and a release script and workflow that check the tag, the workspace version and the changelog agree. Each release states the rule-set versions it was tested against; the latest, 0.4.0, was tested against the CEN EN 16931 validation artefacts 1.3.17, Peppol BIS Billing 3.0.22, Factur-X 1.09.2, XRechnung 3.0.2 and the French e-invoicing rules (FNFE-MPE) 1.4.0.04.
  • Same checks everywhere. CI and a local run use the same script: see Build and test.
